# AGENTS.md

Browser game (vanilla JS ESM, no build step) that spins wheels to generate a character, then runs it through 3 scenarios. Authoritative spec: `wheel of fortune v0.5.md`; requirement IDs (`FR-*`, `C-*`, `NFR-*`) are cited in code comments and test names.

## Commands

- `npm run lint` — eslint .
- `npm run typecheck` — `tsc --noEmit` (checks JSDoc types in src/, sim/, test/)
- `npm test` — `vitest run`; single file: `npx vitest run test/m1a.test.js` or `npm test -- m1a`
- `npm run sim [N]` — headless sim, default 100000 runs. Validates data first (exit 1 on any validation error or runtime throw), prints distributions, writes `data/percentiles.json`.
- Verify with all three: lint, typecheck, test. There is no CI config; nothing runs them for you.

## Hard rules

- `src/core/` must not reference `Math.random`, `Date`, `performance`, `document`, `window`, `fetch` — enforced by ESLint (`no-restricted-globals`/`-properties`), which fails lint. All randomness comes from `src/core/rng.js` (xmur3+sfc32, stream key `master|stageId|redoCount`); every random choice is exactly one draw through `src/core/picker.js`.
- Content boundary (spec §17): never edit `data/` — balance numbers, `[TUNE]` values and flavor text are human-authored. The only exception is `data/percentiles.json`, generated by `npm run sim`. When validation or sim fails on data, report it; do not "fix" the data. Broken test fixtures live in `test/fixtures/`, never `data/`.
- Core is pure over a plain `data` object; loading happens outside core (`fs` in sim and tests, `fetch` in the future browser app). Each test file defines its own `loadData()`.
- Every `.js` in src/sim/test starts with `// @ts-check` and uses JSDoc types — this is a JS project, not TS (tsconfig: `strict: false`, `checkJs: false`, per-file `@ts-check` is what typechecks).

## Spec vs. code (read before "fixing" a mismatch)

Post-spec amendments are implemented in code+tests but not fully reflected in `wheel of fortune v0.5.md`:

- Tag field is `blockedBy`, not `counters` as spec §10 shows.
- `resolveFight` takes no rng; it returns `{entries, harmClass}` and the caller picks via `picker.js`. Contest trace entries carry `meta: {harmClass}`. Scenario stream key: `scenario:${scenarioId}:${stepId}`. Record: `reports/CHECKPOINT-C-SUMMARY.md`, commit `f725dcd`.
- Spec §13 `--prose N` flag and `sim/diff.js` do not exist; sim takes a positional run count only.

When spec and tests disagree, check git log for an amendment commit first; the tests encode the current contract.

## Architecture (`src/core/`)

- `run.js` orchestrator: `generateRun(data, masterSeed, redoMap)` → `{character, band, effStr, scenarios, trace, logProbability}`. Stages run in `config.stageOrder`, then `chain.js` picks 3 scenarios for the band fixed at chain start.
- `mods.js` is the only place stage-table mutations are allowed (closed op list: `shiftTier`, `shiftOffset`, `shiftPowerCount`, `scaleWeight`). Stage-specific rule code elsewhere violates spec FR-C1.
- `stats.js`: effStr / canHarm / fight / check math. `scenario.js`: step-graph execution. `validate.js`: pure, returns `{valid, errors, warnings}`; called by tests and sim.
- Level math: `L = (10 - tier) + frac`, `L ∈ [0, 11)`, `tier = 10 - floor(L)`; higher L is stronger. Test helper `L(tier, frac = 0.5)` in `test/m1a.test.js`.
- No `src/ui/` or browser entrypoint exists yet. UI will only replay traces, never recompute odds (FR-A3).

## Testing

- `test/m0.test.js` — M0 acceptance: determinism, stage independence, picker properties (fast-check), one broken fixture per validation rule.
- `test/m1a.test.js` — M1a acceptance: monotonicity/steepness/bypass/flee via `resolveFightAndPick` helper; deterministic rng stubs like `() => 0.5`.
- Gotcha: `sim/run.js`, `m0.test.js` and `m1a.test.js` each hardcode `data/scenarios/basic.json`. Adding a scenario file means updating all three loaders.
- Check `git status` before assuming a clean baseline — the tree may hold WIP.
